# Database

The additive RAG migration `202610290001_rag_agents` preserves existing projects and payments. It adds ProjectDocument (private original bytes/hash), DocumentChunk (source location/text/project scope and real embedding arrays/model), and EvaluationJob (stages/events/status/lease/report link). Requirements gain relative weights and exact citation references; submissions gain repository URL/requested ref/pinned commit/tree and untrusted setup notes; VerificationRun gains the full structured report; REJECTED is a milestone state. Payment gains baseAmountMinor/tipMinor, backfilled without changing old totals, with a database base+tip=total constraint. A partial unique index prevents two RUNNING evaluations per milestone. `proofpay_cosine` provides exact array-vector similarity. No new vector-service account or extension is needed. Migration SQL also bounds positive weights and vector dimensions. See RAG_VERIFICATION.md for query isolation and scale limits.

PostgreSQL 17 with Prisma 7.10.1. The initial migration is versioned in prisma/migrations. Runtime uses @prisma/adapter-pg and pg; Prisma CLI reads DATABASE_URL from prisma.config.ts.

Users hold hashed passwords and a fixed client/freelancer role. Projects relate a registered client and freelancer. Milestones store integer minor units and a restricted two-decimal currency. Specifications preserve immutable prior requirement versions and each party's agreement timestamp. Submissions belong to a specification version; evidence stores a safe filename, validated MIME type, private bytes and SHA-256. Verification runs reference the submission and criterion IDs. Client decisions preserve rationale and version. Payments have unique milestone, order and capture identifiers. Webhook events deduplicate by verified PayPal event ID. Audit events track project mutations. Rate limits use atomic PostgreSQL upserts. Delivery records form the optional Zapier outbox.

Run npm run db:local for the optional development launcher, or docker compose up -d db, or supply an external PostgreSQL connection. Then npm run db:migrate. Do not run both local database options on port 5438 simultaneously.

For fictional demo data explicitly set ENABLE_DEMO=true, then npm run db:seed. Seed is additive and does not overwrite existing users or projects. Never use the published demo passwords in a real-user deployment. Tests create clearly labeled synthetic users and projects in the configured database; use a dedicated test database for CI. No destructive reset command runs automatically.

The local database is in ignored .data/postgres. Keep backups for important records. Production deployments require an operator-defined retention, backup, restore and deletion policy. Uploaded content is limited to 1 MB per file and 10 files per submission; database-backed storage is sufficient for this prototype, not a substitute for large-scale object storage.
